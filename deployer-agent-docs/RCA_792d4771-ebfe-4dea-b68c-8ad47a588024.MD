# RCA — "Error occurred" uploading video to Hall of Winners gallery (prizeleague.co.uk)

## Summary
The failing requests in production are **`PUT /api/admin/draw-studio/recordings/{rid}/chunks/{index}` returning HTTP 500**, not the paid-winners media endpoints the report named. The paid-winners chunked flow is actually healthy in prod (see below). The Draw Studio recording chunked-upload flow — which produces the `dsv_*` videos shown in the Hall of Winners gallery — crashes because it stores chunk files on **pod-local `/tmp`**, which is not shared across the app's **2 production replicas**.

## Exact failing request + error (from backend logs, run 792d4771, last 24h)
```
PUT /api/admin/draw-studio/recordings/dsv_a05704ebfa7047/chunks/0  -> 500 Internal Server Error
PUT /api/admin/draw-studio/recordings/dsv_a73f1f9cbd8f49/chunks/0  -> 500 Internal Server Error
PUT /api/admin/draw-studio/recordings/dsv_b438b4396cca46/chunks/0  -> 500 Internal Server Error

Traceback (most recent call last):
  File "/app/backend/routers/draw_studio_ops_routes.py", line 260, in upload_chunk
FileNotFoundError: [Errno 2] No such file or directory: '/tmp/draw_studio_recordings/dsv_a05704ebfa7047/0000'
```

## Root cause (proven)
`backend/routers/draw_studio_ops_routes.py`:
- `REC_DIR = "/tmp/draw_studio_recordings"` (line 25) — node-local ephemeral disk.
- `init_recording` (`POST /recordings`, line ~245) does `os.makedirs(os.path.join(REC_DIR, rid))` — the per-upload directory is created **only on whichever replica serves the `start` call**.
- `upload_chunk` (`PUT /recordings/{rid}/chunks/{index}`, line 260) does `open(os.path.join(REC_DIR, rid, f"{index:04d}"), "wb")`.

Production tier `tier_0` runs **2 replicas, no HPA, no session affinity** (confirmed via get_tier: replicas=2). The chunk PUTs are load-balanced independently of the `start` call. When a chunk PUT lands on the replica that did NOT create the directory, the parent folder doesn't exist → `FileNotFoundError` → 500. The frontend surfaces this as the generic "error occurred."

This matches every observed fact:
- **Preview returns 200 for the same 5 MB mp4** — preview runs a single pod, so `start` + all chunk writes always share one filesystem.
- **One prod recording succeeded** (`dsv_413e6d54994442` chunks 0,1,2 → 200, complete → 200) — that upload happened to have `start` and all chunks routed to the same replica.
- Object storage is **not** the problem: the successful `complete` call (`put_object`) returned 200, and all paid-winners `put_object` uploads succeed. No storage-key / bucket / credential errors in logs. No 413/415/timeout at ingress for these paths.

## The paid-winners flow the report named is healthy
`backend/routers/paid_winners_routes.py` chunked media (`/contests/{cid}/media/chunked/start|{upload_id}/{index}|complete`) stores chunks in **MongoDB** (`pw_media_chunks` collection via `db.pw_media_chunks.update_one(...upsert=True)`), not local disk — so it is replica-safe. In the last 24h prod logs this flow ran cleanly: `start` → 200 and chunks 0–45 (upload_id `17a5a67a...`) all → 200. It is the correct pattern; the Draw Studio flow should copy it.

## Recommended fix (Code — E1)
Make the Draw Studio chunked upload replica-safe. Preferred: mirror the already-working paid-winners pattern — persist chunks in MongoDB instead of `/tmp`.
In `backend/routers/draw_studio_ops_routes.py`:
- `init_recording`: drop the `os.makedirs(REC_DIR/rid)`; just create the DB upload record.
- `upload_chunk` (line 260): replace `open(.../f"{index:04d}", "wb")` with an upsert into a chunks collection (e.g. `db.draw_studio_chunks.update_one({"recording_id": rid, "index": index}, {"$set": {"data": Binary(data)}}, upsert=True)`), same as `pw_media_chunks`.
- `complete_recording` (line ~270): read/concatenate chunks from the DB (sorted by index), `put_object(...)` as today, then `delete_many` the chunk docs instead of `shutil.rmtree`.

Alternative (not recommended as the real fix): run a single replica or enable sticky sessions so `start` + chunks hit the same pod — but local `/tmp` is still lost on any pod restart/reschedule mid-upload, so the DB-backed approach is the durable fix.

## Verification note
Mechanism verified from the live traceback + source + tier replica count (2). Not reproduced in an eph sandbox — the sandbox is single-pod and has no live DB, so the multi-replica race cannot be exercised there.
